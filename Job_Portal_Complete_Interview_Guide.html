Chapter 3: Database Design (MongoDB + Mongoose)

3.1 Why MongoDB?

  • Schema flexibility — user profiles have nested objects (bio, skills array, photo URL). Relational DBs would need multiple tables + JOINs.
  • JSON-native — JavaScript objects map directly to MongoDB documents. No ORM impedance mismatch.
  • Embedded documents — user.profile.skills is an array inside the user document. In SQL, this would need a separate user_skills junction table.
  • ObjectId references — mongoose.Schema.Types.ObjectId with ref enables .populate() (similar to SQL JOINs).

🎯 Interview Q: Why is profile an embedded object instead of a separate collection?
Answer: Because a user's profile is always accessed alongside the user (1:1 relationship). Embedding eliminates an extra database query. In MongoDB, if you always read/write related data together, embed it. If it's accessed independently or has a many-to-many relationship, use references.
🎯 Interview Q: Why store password as a hash and not plaintext?
Answer: Security. If the database is breached, attackers can't read actual passwords. bcrypt.hash(password, 10) creates a one-way hash with 10 salt rounds. Even the same password produces different hashes (due to unique salt per hash). Verification uses bcrypt.compare(input, storedHash).

Job Schema (job.model.js)

Key fields: title, description, requirements: [String] (split from comma-separated input), salary, experienceLevel, location, jobType, position (openings count), company: ObjectId → Company, created_by: ObjectId → User, applications: [ObjectId → Application]

🎯 Interview Q: Why is applications stored as an array of ObjectIds in the Job document?
Answer: This enables efficient .populate("applications") to load all applicants in one query. The recruiter's Applicants page needs to display all applicants for a job — without this array, we'd need a separate Application.find({job: jobId}) query. The tradeoff: the Job document grows with each application, but for typical job postings (10-500 applicants), this is acceptable.

Application Schema (application.model.js)

Application {
  job:       ObjectId → Job,
  applicant: ObjectId → User,
  status:    "pending" | "accepted" | "rejected"
}

This is a junction/bridge model that connects Users to Jobs in a many-to-many relationship. One user can apply to many jobs; one job can have many applicants.

Company Schema (company.model.js)

Fields: name (unique), description, website, location, logo (Cloudinary URL), userId: ObjectId → User. A recruiter must create a company before posting jobs.

🎯 Interview Q: Why is middleware order important in Express?
Answer: Express processes middleware in the order they are registered. express.json() must come before routes, otherwise req.body will be undefined. cookieParser() must come before auth middleware, otherwise req.cookies is unavailable. If CORS middleware comes after routes, preflight OPTIONS requests will fail.

Chapter 5: Authentication & Security System

5.1 JWT (JSON Web Token) Deep Dive

What is JWT? A digitally signed token containing user data. Structure: header.payload.signature

Token Creation (Login):

const token = jwt.sign(
  { userId: user._id },              // Payload (data stored in token)
  process.env.JWT_SECRET,             // Secret key (never exposed)
  { expiresIn: "1d" }                // Expires in 24 hours
);

res.cookie("token", token, {
  maxAge: 1 * 24 * 60 * 60 * 1000,   // 24 hours in milliseconds
  httpOnly: true,                     // JavaScript cannot access
  sameSite: "Strict",                 // CSRF protection
});

Token Verification (Every Protected Request):

const token = req.cookies.token;        // Read from cookie
const decoded = jwt.verify(token, JWT_SECRET); // Verify signature
req.id = decoded.userId;                // Attach to request

🎯 Interview Q: Why use httpOnly cookies instead of localStorage for JWT?
Answer: httpOnly cookies are inaccessible to JavaScript. If there's an XSS vulnerability (e.g., injected script on the page), the attacker cannot read the JWT and steal the session. With localStorage, any JavaScript on the page (including injected malicious scripts) can read localStorage.getItem("token"). The tradeoff: cookies are automatically sent with every request (via withCredentials: true), which is why we also need sameSite: "Strict" to prevent CSRF.
🎯 Interview Q: What are salt rounds in bcrypt?
Answer: The number 10 in bcrypt.hash(password, 10) is the cost factor (2^10 = 1024 iterations). Higher = slower = harder to brute force. Each hash has a unique random salt embedded in it, so the same password produces different hashes. This prevents rainbow table attacks. Industry standard is 10-12 rounds.

Chapter 6: File Upload Pipeline

6.1 The Upload Flow

1
Frontend: User selects file → stored in FormData with key "file"
2
Multer middleware: multer.memoryStorage().single("file") reads the upload into req.file.buffer (RAM, not disk)
3
DataURI conversion: getDataUri(req.file) converts Buffer → "data:image/png;base64,iVBOR..."
4
Cloudinary upload: cloudinary.uploader.upload(dataURI) → returns { secure_url: "https://res.cloudinary.com/..." }
5
MongoDB save: user.profile.profilePhoto = secure_url → user.save()
🎯 Interview Q: Why use memoryStorage instead of diskStorage in Multer?
Answer: With memoryStorage, the file stays in RAM as a Buffer. This is ideal because we immediately convert it to a DataURI and upload to Cloudinary — we never need to save it to disk. diskStorage would write to a temp file, then we'd read it back, then upload, then delete the temp file — unnecessary I/O. The tradeoff: large files could consume too much RAM, but for resumes and profile photos (< 10MB), this is fine.

9.2 RESET_STORE Pattern

const rootReducer = (state, action) => {
  if (action.type === "RESET_STORE") {
    state = undefined;  // Forces all slices to return initialState
  }
  return appReducer(state, action);
};
🎯 Interview Q: Why dispatch RESET_STORE on login, not just on logout?
Answer: Because redux-persist saves state to localStorage. If User A logs out but the persist data isn't fully cleared (race condition, browser crash, etc.), User B logging in on the same browser would see User A's saved jobs, applied jobs, and private data. Dispatching RESET_STORE right before setUser(newUser) guarantees a clean slate.

Chapter 14: Technical Interview Q&A (50+ Questions)

🔹 JavaScript / Node.js

Q1: What is "type": "module" in package.json?
It enables ES Module syntax (import/export) instead of CommonJS (require/module.exports). Without it, Node.js uses CommonJS by default. This project uses import express from "express" everywhere. Note: file extensions must be included in imports (./utils/db.js).
Q2: Explain async/await vs callbacks. Why does this project use async/await?
Callbacks lead to "callback hell" (nested functions). Promises flatten the chain. async/await makes asynchronous code look synchronous. Every controller uses async (req, res) => { try { await db.find() } catch { res.status(500) } }. The try/catch handles both sync and async errors.
Q3: What is the event loop? How does Express handle multiple requests?
Node.js is single-threaded with an event loop. When a request hits an await mongoose.find(), the thread doesn't block — it delegates the I/O to the OS/libuv thread pool and processes other requests. When the DB responds, the callback is placed in the event queue and executed. This is why Node.js handles thousands of concurrent connections despite being single-threaded.
Q4: What is middleware in Express? Name the types used in this project.
(1) Application-level: app.use(express.json()) — runs on every request. (2) Router-level: router.post("/login", login) — runs on specific routes. (3) Third-party: cors(), cookieParser(), multer(). (4) Custom: isAuthenticated, optionalAuth. Middleware executes in order via next().
Q5: What is CORS and why is it needed?
Cross-Origin Resource Sharing. Browsers block requests from one origin (localhost:5173) to another (localhost:5011) by default (Same-Origin Policy). The backend must explicitly allow the frontend's origin. cors({origin: ["http://localhost:5173"], credentials: true}) tells the browser: "This origin is allowed, and you may send cookies."

🔹 React / Frontend

Q6: Explain Virtual DOM.
React maintains a lightweight copy of the real DOM in memory. When state changes, React creates a new Virtual DOM, diffs it against the old one (reconciliation), and only updates the changed DOM nodes (batch update). This is why React is fast — it minimizes expensive real DOM operations.
Q7: What are React hooks? Which ones does this project use?
useState — local state (form inputs in Login.jsx). useEffect — side effects (data fetching in custom hooks). useNavigate — programmatic routing. useParams — read URL params (jobId). useSelector — read Redux state. useDispatch — dispatch Redux actions.
Q8: What is the purpose of useEffect's dependency array?
[] — runs once on mount (like componentDidMount). [searchedQuery] — runs when searchedQuery changes. No array — runs on every render (usually a bug). In useGetAllJobs, the dependency is [searchedQuery] — so it re-fetches jobs whenever the user searches something new.
Q9: Why use createBrowserRouter instead of <BrowserRouter>?
createBrowserRouter (React Router v6.4+) is the data API router. It supports loaders, actions, and error elements. It's defined as a configuration object (array of routes), making it easier to reason about all routes in one place (App.jsx).
Q10: What is Tailwind CSS and why use it instead of regular CSS?
Utility-first CSS: className="bg-blue-500 p-4 rounded-lg text-white". No naming CSS classes. No switching between CSS and JSX files. Consistent design system via config. Purges unused classes in production (tiny CSS bundle). The tradeoff: long class strings in JSX.

🔹 MongoDB / Database

Q11: MongoDB vs SQL — when to use which?
MongoDB: flexible schemas, nested documents, rapid iteration, JavaScript-native. Good for: social media profiles, content management, real-time apps. SQL: strict schemas, complex JOINs, transactions, data integrity. Good for: banking, inventory, relationships-heavy data. This project uses MongoDB because user profiles have varying fields and the schema evolves during development.
Q12: What is .populate() and what SQL operation is it equivalent to?
.populate("company") replaces the ObjectId reference with the actual document from the referenced collection. It's equivalent to SQL LEFT JOIN. Under the hood, Mongoose fires a second query: Company.find({_id: {$in: [id1, id2]}}). Deep populate: .populate({path: "applications", populate: {path: "applicant"}}) is like a multi-table JOIN.
Q13: What does {timestamps: true} do in Mongoose?
Automatically adds createdAt and updatedAt fields to every document. Mongoose manages them — createdAt is set on insert, updatedAt on every .save() or findOneAndUpdate(). Useful for sorting (newest first) and auditing.
Q14: Explain the $regex query used in job search.
Job.find({title: {$regex: keyword, $options: "i"}}) — performs case-insensitive substring search. "i" flag = case insensitive. $or searches both title AND description. This is simpler than full-text search but less performant on large datasets (no index). For production, you'd use MongoDB Atlas Search or Elasticsearch.

🔹 Authentication & Security

Q15: JWT vs Session-based auth — what's the difference?
JWT (this project): Stateless. Token contains user data. Server doesn't store sessions. Scales horizontally. Sessions: Stateful. Session ID stored server-side (Redis/DB). More control (can revoke instantly). JWT tradeoff: can't revoke before expiry. This project uses 1-day expiry as mitigation.
Q16: What is CSRF and how does this project prevent it?
Cross-Site Request Forgery: attacker crafts a malicious page that sends a request to your backend (which auto-includes the victim's cookies). sameSite: "Strict" on the JWT cookie prevents this — the cookie is NOT sent on cross-origin requests (e.g., from evil-site.com to localhost:5011).
Q17: What is XSS and how does httpOnly prevent it?
Cross-Site Scripting: attacker injects JavaScript into the page. If JWT is in localStorage, the injected script reads it with localStorage.getItem("token"). With httpOnly: true, JavaScript cannot access the cookie at all — only the browser can send it in HTTP headers.

🔹 AI / ML Features

Q18: What is RAG (Retrieval Augmented Generation)?
RAG combines information retrieval with text generation. Instead of asking the LLM to "remember" facts, you retrieve relevant data (candidate resumes, skills, match scores) and inject it into the prompt. The LLM generates answers grounded in this context. This prevents hallucination and ensures answers are based on actual data.
Q19: What is semantic similarity and how is it used for matching?
Semantic similarity measures how close two texts are in meaning (not just exact keyword match). sentence-transformers converts text to high-dimensional vectors (embeddings). Cosine similarity between resume embedding and job description embedding gives a 0-100% score. This catches synonyms: "frontend developer" matches "UI engineer" even though the words are different.
Q20: How does the skill deduplication work?
formatCleanSkills() normalizes each skill: lowercase, remove dots/hyphens, trim whitespace. Then looks up STANDARD_SKILL_NAMES map: "react js" → "React", "nodejs" → "Node.js". Uses a Set (dedupKey = lowercase alphanumeric only) to ensure "React", "react.js", "ReactJS" all become one "React" entry.

17.1 Reconciliation & Fiber Architecture

Q: Explain React's reconciliation algorithm.
Answer: When state changes, React builds a new Virtual DOM tree. It then diffs the new tree against the old one using two heuristics: (1) Elements of different types produce different trees — React tears down the old tree and builds a new one. (2) Elements with stable key props can be matched across renders. This reduces the O(n³) DOM diffing problem to O(n). React then batch-applies only the minimal set of real DOM mutations. React Fiber (React 16+) made this interruptible — React can pause rendering work to handle higher-priority updates like user input.

// Between each phase: process.nextTick() and Promise microtasks
Q: What's the difference between process.nextTick() and setImmediate()?
process.nextTick(): Fires BEFORE the event loop continues to the next phase. It's a microtask — it has highest priority. setImmediate(): Fires in the Check phase — after I/O events. Promise .then(): Also a microtask, fires after nextTick. Order: nextTick → Promise → setImmediate → setTimeout.

18.2 How Express Handles 10,000 Concurrent Requests

Q: Node.js is single-threaded. How can this backend handle thousands of users?
Answer: The single thread only handles JavaScript execution. All I/O (MongoDB queries, Cloudinary uploads, HTTP calls to AI service) is delegated to the libuv thread pool (default: 4 threads) or the OS kernel (epoll/kqueue). When await User.findOne({email}) runs, the thread is FREE to handle other requests. When MongoDB responds, the callback enters the event queue. This non-blocking I/O model lets a single Node.js process handle 10K+ concurrent connections. CPU-intensive tasks (bcrypt hashing) DO block — that's why bcrypt uses a native C++ addon with its own threads.

In this project, the resume upload currently loads the entire PDF into memory (memoryStorage). For large files, you'd use a stream: pipe the upload directly to Cloudinary without buffering the whole file in RAM. Also, the PDF text extraction could use streaming to handle multi-hundred-page resumes.

19.1 Indexing — The #1 Performance Topic

Q: What indexes should this project have? Why?

19.2 Aggregation Pipeline

Q: What is the aggregation pipeline? Give an example for this project.
Answer: Aggregation pipeline processes documents through stages: $match (filter), $group (aggregate), $sort, $project (reshape), $lookup (join), $unwind (flatten arrays). Example — get the number of applicants per job for a recruiter:
Job.aggregate([
  { $match: { created_by: recruiterId } },      // Filter recruiter's jobs
  { $lookup: {                                    // JOIN with applications
    from: "applications",
    localField: "_id",
    foreignField: "job",
    as: "apps"
  }},
  { $project: {                                   // Reshape output
    title: 1,
    applicantCount: { $size: "$apps" },
    acceptedCount: {
      $size: { $filter: { input: "$apps", cond: { $eq: ["$$this.status", "accepted"] }}}
    }
  }},
  { $sort: { applicantCount: -1 } }              // Most applicants first
]);

19.4 Transactions

Q: What are MongoDB transactions? Where should this project use them?
Answer: Transactions ensure multiple operations are atomic (all succeed or all fail). In this project, applyJob() does TWO writes: (1) Create Application (2) Push applicationId to Job.applications[]. If step 2 fails, you have an orphan application. With a transaction: 
const session = await mongoose.startSession();
session.startTransaction();
try {
  const app = await Application.create([{...}], {session});
  await Job.updateOne({_id: jobId}, {$push: {applications: app._id}}, {session});
  await session.commitTransaction();
} catch (e) {
  await session.abortTransaction(); // Both writes rolled back
}
Requires MongoDB replica set (MongoDB Atlas has this by default).

Q: What is the N+1 query problem? Does this project have it?
Answer: N+1 occurs when you fetch N items, then fire a separate query for each item's related data. Example: getApplicants() fetches a job, then .populate("applications") fires 1 query for all applications. Then .populate({path: "applications", populate: "applicant"}) fires N queries (one per applicant). This IS an N+1 problem. Fix: use $lookup aggregation for a single query, or accept the trade-off for small datasets (< 500 applicants).

Chapter 23: Project Weaknesses — Gotcha Questions

⚠️ Interviewers love asking about weaknesses to test your self-awareness and engineering maturity. Here's how to answer every gotcha.
GOTCHA: "Your job search uses $regex. That's terrible for performance!"
"You're right. $regex with a leading wildcard can't use indexes and triggers a full collection scan. For our dev-scale dataset (< 1000 jobs), this is acceptable. For production, I'd switch to MongoDB Atlas Search which provides full-text search with fuzzy matching, relevance scoring, and auto-complete — all using Apache Lucene under the hood. Alternatively, Elasticsearch. The migration is straightforward: create a search index on title and description, replace the find({$regex}) with an aggregation $search stage."
GOTCHA: "You have no pagination. Loading all jobs at once will crash with 100K records."
"Correct. The fix is cursor-based pagination: Job.find(filter).sort({createdAt: -1}).skip((page-1)*limit).limit(limit) and return {jobs, totalCount, page, totalPages}. Frontend adds 'Load More' button or infinite scroll. Skip-based pagination has its own issues at scale (skip is O(n)) — for very large datasets, I'd use cursor-based pagination: {_id: {$lt: lastId}} which uses the index."
GOTCHA: "There are no tests. How do you know this works?"
"We verified functionality through manual testing during development and peer code reviews. I acknowledge automated tests are essential for a production system. If I were to add them now, I'd prioritize: (1) Unit tests for utility functions like formatCleanSkills() and computeAccurateMatch() — they're pure functions, easiest to test. (2) Integration tests for the auth flow — register, OTP, login is the most critical path. (3) Component tests for forms — ensure validation works correctly. This would give 80% coverage on the most critical paths with minimal effort."
GOTCHA: "What happens if someone sends 10,000 login requests per second?"
"Currently, nothing prevents it — there's no rate limiting. A brute-force attack could guess passwords or exhaust bcrypt's CPU. The fix is express-rate-limit: rateLimit({windowMs: 15*60*1000, max: 5, message: 'Too many attempts'}) Applied to /login, /register, /verify-otp. For distributed rate limiting (multiple server instances), use Redis-backed rate limiting. Additionally, add exponential backoff: after 3 failed attempts, lock the account for 5 minutes."
GOTCHA: "Is there any input sanitization? What about NoSQL injection?"
"Mongoose provides basic protection — it casts inputs to the schema types, rejecting unexpected types. But raw user input in $regex is dangerous: a user could input .* to match everything or crafted regex for ReDoS (Regular Expression Denial of Service). The fix: (1) Escape regex special characters with input.replace(/[.*+?^${}()|[\]\\]/g, '\\$&'). (2) Use mongo-sanitize middleware to strip $ operators from user input. (3) Validate and whitelist input formats with joi or express-validator."
GOTCHA: "What if two users apply to the same job at the exact same time?"
"This is a race condition. The current duplicate check (Application.findOne({job, applicant})) is not atomic. Between the check and the Application.create(), another request could slip in. Fix: (1) Create a compound unique index: Application.createIndex({job: 1, applicant: 1}, {unique: true}). MongoDB will reject the duplicate at the database level, regardless of race conditions. (2) Wrap in a transaction. The unique index is the simpler and more reliable solution."
GOTCHA: "JWT can't be revoked before expiry. What if a user's token is stolen?"
"True. Mitigation strategies: (1) Short expiry (currently 1 day — could reduce to 1 hour). (2) Refresh token rotation: short-lived access token (15 min) + long-lived refresh token (7 days) in separate httpOnly cookies. (3) Token blacklist: store revoked token IDs in Redis with TTL matching the token's remaining lifetime. On logout, add token to blacklist. (4) Token versioning: store a version counter on the user document. If the version in the token doesn't match, reject it. Increment on password change."
GOTCHA: "Your AI service has a 60-second timeout. Users will see a spinning page."
"Agreed. The UX for long AI operations should be asynchronous. Instead of blocking: (1) Frontend sends request. (2) Backend creates a 'pending' task in MongoDB, returns taskId immediately. (3) Background worker (Bull queue) processes the AI call. (4) Frontend polls GET /api/ai/task/:taskId every 3 seconds (or uses WebSocket). (5) When complete, frontend shows results. This is the async request-reply pattern."

24.1 HTTP Protocol

Q: What happens when you type http://localhost:5173 and press Enter?
(1) Browser resolves localhost → 127.0.0.1 (loopback). (2) TCP 3-way handshake with port 5173. (3) Browser sends GET / HTTP/1.1 request. (4) Vite dev server responds with index.html. (5) Browser parses HTML, discovers <script src="/src/main.jsx">. (6) Browser requests main.jsx. Vite transforms JSX → JS on-the-fly via esbuild. (7) React mounts, renders components. (8) Components call axios.get("http://localhost:5011/api/job/get"). (9) Browser sends preflight OPTIONS request (CORS). (10) Backend responds with CORS headers. (11) Browser sends actual GET with cookies. (12) Backend responds with JSON. (13) React updates state → re-renders UI.

24.4 REST vs GraphQL

Q: This project uses REST. When would you use GraphQL instead?
REST (this project): One endpoint per resource. Simple, cacheable, well-understood. Good when: data shape is predictable, CRUD operations, team is familiar with REST. GraphQL: One endpoint, client specifies exact fields. Good when: frontend needs different data shapes for mobile vs web, deeply nested data, reducing over-fetching. Example: the Applicants page fetches a job, then applicants, then each applicant's resume analysis. In GraphQL, this would be ONE query. In REST, it's multiple .populate() calls or N+1 queries.

24.5 WebSockets vs HTTP

Q: When would you add WebSockets to this project?
HTTP: Request-response. Client asks, server answers. No persistent connection. This project uses HTTP for everything. WebSockets: Full-duplex, persistent connection. Server can push data to client. Use for: (1) Real-time notifications (recruiter accepts → student sees instantly). (2) Live chat with AI assistant (stream responses token by token). (3) Applicant status changes. Implementation: Socket.io on backend, socket.io-client on frontend. Server emits io.to(userId).emit("statusUpdate", data).

24.6 OAuth 2.0 Flow

Q: The project's email system uses OAuth2 as a fallback. Explain OAuth2.
OAuth 2.0 lets an app access a user's data on another service without knowing their password. In this project's mailer: (1) Developer creates OAuth2 credentials in Google Cloud Console. (2) Gets a refresh_token through one-time consent flow. (3) On each email send, Nodemailer uses client_id + client_secret + refresh_token to get a short-lived access_token from Google. (4) Uses that access_token to send email via Gmail API. More secure than App Passwords because tokens can be scoped and revoked.

24.7 HTTPS & SSL/TLS

Q: This runs on HTTP in development. What changes for production?
HTTPS is mandatory in production for: (1) Encrypting JWT cookies in transit (prevents network sniffing). (2) Browser requirement for sameSite: "None" cookies if frontend and backend are on different domains. (3) User trust and SEO. Setup: Deploy behind a reverse proxy (Nginx or cloud load balancer) that terminates SSL. Use Let's Encrypt for free certificates. The Node.js app itself doesn't need to change — the proxy handles HTTPS.
